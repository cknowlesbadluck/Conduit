# Conduit v0.5 Coordination Design

## Goal
Evolve Conduit from a secure MCP coordination foundation into a project-agnostic multi-project coordination plane with authenticated actor identity, first-class projects/resources, and stronger lifecycle guarantees.

## Current State
Conduit already exposes an authenticated MCP endpoint, agent registration/discovery, task lifecycle operations, contacts, tool/MCP endpoint discovery, activity history, and PostgreSQL persistence. The current store accepts caller-supplied logical agent identifiers for write operations, and the existing data model has no project scope or generic resource registry.

## Design Principles

1. **Project-agnostic identity:** Conduit remains independent of any application. Projects are data domains inside Conduit, not architectural dependencies.
2. **Authenticated actor vs logical agent:** OAuth `sub` identifies the authenticated actor. A logical Conduit agent ID is a registered coordination identity. Write operations must not allow an actor to silently impersonate another agent.
3. **Explicit privileged orchestration:** Normal actors operate as themselves. A narrowly defined orchestrator capability may act on behalf of other logical agents only when explicitly granted by the authorization layer; the implementation must not invent new OAuth scopes that are not configured.
4. **Project scoping is optional:** Existing single-project or projectless workflows continue to work. New records may be associated with a project. Lists and context accept an optional project filter.
5. **Resources are generic:** A resource represents a development asset or integration reference such as a repository, service, environment, documentation source, MCP endpoint, or external system. Resources are metadata and references; Conduit does not execute arbitrary remote URLs merely because they are registered.
6. **No credential storage in records:** Resource metadata must never require embedding API keys, bearer tokens, passwords, or other secrets in ordinary resource fields.
7. **Durable and in-memory parity:** PostgreSQL and memory implementations expose the same observable semantics.
8. **Free-first operation:** The feature set must use the existing Node/TypeScript/PostgreSQL stack and existing deployment model without adding paid infrastructure requirements.

## Data Model

### Projects
Fields:
- `id`: stable string primary key
- `name`: required display name
- `description`: optional description
- `createdBy`: logical agent ID of creator
- `createdAt`, `updatedAt`

Projects are independent records. No project is privileged or canonical.

### Resources
Fields:
- `id`: stable string primary key
- `projectId`: nullable project reference
- `name`: required display name
- `description`: required description
- `kind`: required classification such as `repository`, `service`, `environment`, `documentation`, `mcp`, or `external`
- `endpoint`: optional URL/reference
- `createdBy`: logical agent ID
- `createdAt`, `updatedAt`

### Tasks
Add nullable `projectId` while retaining existing lifecycle and ownership fields.

### Contacts and Tools
Add nullable `projectId` and `createdBy` so new records can be attributed and scoped without breaking existing records.

## Identity and Authorization

The authenticated request supplies `AuthInfo` containing `clientId`, scopes, and token claims including `sub`. Conduit derives an actor key from the authenticated subject, with client ID available as supporting identity metadata.

On `agent_register`, the authenticated actor may register/update the logical agent identity associated with that actor. The store records the binding. Subsequent normal write operations derive the actor's logical agent from the authenticated context rather than trusting arbitrary `agentId`, `createdBy`, or `fromAgent` values.

For compatibility with existing MCP clients and test-only in-memory calls, the store functions retain explicit logical-agent parameters. The MCP layer is responsible for binding those parameters to the authenticated actor before invoking the store. Existing unauthenticated development mode continues to use explicit IDs because it is intentionally outside production authentication.

When a caller requests an action for another agent, Conduit rejects it unless an already configured authorization scope explicitly permits that behavior. No new privileged OAuth scope is introduced by v0.5; if no configured privileged capability exists, cross-agent impersonation remains unavailable.

## MCP Surface

New tools:
- `project_create`
- `projects_list`
- `resource_register`
- `resources_list`

Existing tools gain an optional `projectId` where meaningful:
- `task_create`
- `task_list`
- `contact_add`
- `contacts_list`
- `tool_register`
- `tools_list`
- `activity_list`
- `conduit_context`

`agent_register` establishes the authenticated actor-to-logical-agent binding. `agent_identity` reports both authentication identity and bound logical agent identity.

## Context
`conduit_context` remains project-agnostic by default and returns a global coordination snapshot. With an optional `projectId`, it returns the same shape filtered to that project plus project metadata. The canonical development context must continue to contain no project-specific identity.

## Validation and Errors
- IDs, names, descriptions, and kinds use bounded Zod validation.
- Resource endpoints, when supplied, must be valid URLs.
- Unknown project IDs are rejected for project-scoped writes.
- Cross-project reads are permitted only when the caller intentionally requests a project or global scope; no project data is leaked through a project-filtered query.
- Ownership failures use deterministic `isError` MCP responses rather than silent mutation.

## Persistence and Migration
Startup initialization uses additive `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements and indexes. Existing rows remain valid with nullable project and creator fields. No destructive migration is required.

## Testing
Tests cover:
- project creation/listing
- resource registration/listing
- project-scoped task filtering
- project-scoped contacts/tools/activity
- actor-to-agent binding
- rejection of impersonation
- valid task claim/complete/handoff through the bound actor
- unknown-project rejection
- memory/PostgreSQL parity where practical
- global context remains project-agnostic
- existing lifecycle behavior remains intact

## Non-Goals
- Direct execution of GitHub, Render, Linear, Supabase, or arbitrary MCP operations.
- Secret management or credential brokering.
- Project-specific hard-coding.
- Introducing a web dashboard as part of the coordination core.
- Replacing the existing OAuth provider.

## Acceptance Criteria
1. An authenticated agent can establish a logical Conduit identity and safely perform its own writes.
2. A caller cannot complete, hand off, or create work while claiming another agent's identity.
3. Multiple unrelated projects can coexist and have isolated project-scoped coordination records.
4. Generic resources can be registered/discovered without turning Conduit into a project-specific integration.
5. Existing unscoped task workflows remain functional.
6. CI typecheck, tests, and build pass.
7. Live health/readiness/OAuth/MCP smoke checks remain green after deployment.
